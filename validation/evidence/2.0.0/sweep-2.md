## Findings

### S2-1 (P3): `rollup --watch` misses a retargeted middle hop of a link chain whose first link sits in a source folder

- Tracked: no. Same defect class as #434 (closed in #439), which fixed chains for sources named directly; this is the variant for a link found inside a source folder.
- Reproduction (Linux, Node 24.21.0, Rollup 4.64.4, dist/): `/tmp/s2scripts/rollup2.mjs`. Layout: `story/a.tw`, `story/link.tw -> ../t/hop.tw`, `t/hop.tw -> one.tw`; plugin `sources: [story]`; after the first build, `t/hop.tw` is replaced by a link to `two.tw` (symlink + rename). Result: `inside-folder { before: 1, after: 1, hasTwo: false }`: no build, the story keeps `one.tw`. Control in the same script with `sources: [story/a.tw, story/link.tw]`: `{ before: 1, after: 2, hasTwo: true }`. The same layout under `vite build --watch` rebuilds (vite3.mjs), and so does `twee-ts -w` (watch1.sh).
- Root cause: `watchPlan()` in src/plugins/watch-targets.ts collects `links` only from `linksOnTheWay(input)` for the named inputs; for the `given` spelling the Rollup plugin uses, `spell()` returns `[path]` and never calls `hopsOf()`, so the hops of a link found while walking a source folder never reach `plan.links`, and `createLinkWatch()` watches nothing for them (no `twee-ts-links-*` folder is even created). The `WatchPlan.links` doc comment promises "the links below a source folder that source discovery follows". Rollup's chokidar follows `story/link.tw` to `t/one.tw`, so replacing `t/hop.tw` raises nothing.
- Contract: docs/plugins.md, Rollup "Watch mode": the plugin "watches the folders that hold the links the inputs are reached through (each hop of a chain …) and starts a build when one of them leads elsewhere".
- Severity: P3, as #434: the next build something else starts reads the new target.
- Suggested issue: "[P3] rollup --watch misses a retargeted hop of a link chain that starts inside a source folder". Invariant: under `rollup --watch`, replacing any link on the way to any input (named or found in a source folder) starts a build. Fix: in `watchPlan`, add the hops of every link found while walking (`isLink(path) ? linksOnTheWay(path)` for the `given` spelling too) to `links`; test the matrix {named file, file found in a folder, file found in a nested folder} × {first link, middle hop, last hop} × {Rollup, Vite}.

### S2-2 (P3): `rollup --watch` fails every build when the temporary folder can't be written and a source is reached through a link

- Tracked: no.
- Reproduction: `TMPDIR=/tmp/s2p/tmpro TMO=60 bash /tmp/s2scripts/node.sh /tmp/s2scripts/rollup2.mjs` (with `/tmp/s2p/tmpro` mode 555; or a TMPDIR that does not exist). The `named-file` variant reports `ERROR EACCES: permission denied, mkdtemp '/tmp/s2p/tmpro/twee-ts-links-XXXXXX'` and writes no output; the same build without links, or without watch mode, succeeds.
- Root cause: `createLinkWatch()` (src/plugins/link-watch.ts:36) calls `mkdtempSync(join(tmpdir(), …))` and `writeFileSync(signal)` without a guard, from the Rollup plugin's `buildStart`, so the error fails the build, and since `linkWatch` stays undefined it fails again on every build. Its sibling for the CLI watch, `openProbe()` in src/folder-stream.ts, catches the same failure and carries on without the probe.
- Severity: P3 (an unusual environment: a read-only or missing TMPDIR in a sandbox or container), but it turns an optional refinement into a hard failure.
- Suggested issue: "[P3] Rollup build watch fails when the link watch cannot create its temporary folder". Fix: catch the failure in `createLinkWatch()`/`buildStart`, warn once that retargeted links will be read with the next build, and continue without the signal file (or place the signal file somewhere the plugin can write, such as the output folder's parent cache); test with a read-only and a missing TMPDIR.

### S2-3 (P4): a repeated field in a format index is reported as "the last one is used" while the entry, or the whole index, is rejected

- Tracked: no.
- Reproduction: `/tmp/s2scripts/remote.mjs` (entry `{"name":"Dup","version":"1.0.0","version":"2.0.0",…}`) gives `Not usable: twine2 entry 0 … $.twine2[0].version repeats the field "version"; the last one is used`; `/tmp/s2scripts/remote2.mjs` (index `{"twine2":[],"twine2":[…]}`) gives `Failed to read format index …: $.twine2 repeats the field "twine2"; the last one is used`, and the build fails with "not available".
- Root cause: `readObject()` in src/json-decode.ts words every `duplicate-key` issue for the lenient readers (StoryData), and src/remote-formats.ts (lines 543 and 580) joins those messages as the reason for rejecting the entry or the index. Rejecting is the documented behaviour for an entry (docs/story-formats.md: "with a repeated member, is skipped"); the message says the opposite. The index-level case is not documented at all.
- Suggested issue: "[P4] Format index diagnostics say a repeated field's last value is used when the entry or index is rejected". Fix: word the issue by its consequence in the index reader ("repeats the field …, so the entry is skipped" / "so the index is not used"), and document the index-level case.

### S2-4 (P3): a link in a source folder whose target can't be reached (a link loop, or a target in a folder that can't be searched) fails the build whatever its name, even when `exclude` leaves it out

- Tracked: no (#160 made the walk stop following folder links; #395 covered a dangling config link).
- Reproduction: `bash /tmp/s2scripts/loop.sh` and `bash /tmp/s2scripts/loop2.sh`: with `ln -s loop lq/loop` (no source extension) `twee-ts --no-remote lq -o lq.html --exclude 'lq/loop'` (also `--exclude '**/loop'`) prints `error: load lq/loop: ELOOP: too many symbolic links encountered` and exits 1 without output; `ln -s ../locked/readme lq/readme` into a mode-000 folder gives `error: load lq/readme: EACCES` likewise. For comparison, an unreadable regular `notes.txt`, an excluded unreadable `u.tw`, and a dangling link are all skipped and the build succeeds.
- Root cause: `walkEntry()` in src/filesystem.ts stats a link's target first and reports any error other than a missing target as `problem('found', 'unreadable', …)`, before it looks at the file type (`unsupported-type` is `ignore` for found inputs) and before `addFile()` applies `exclude`. So the input policy's type and exclusion rules never get a say.
- Contract: docs/cli.md "Inputs That Can't Be Used" (a file type the role doesn't load, found in a folder: skipped without a word) and `exclude` ("Leave out source files matching a glob"); Tweego filters by extension before reading, so it skips such a link.
- Severity: P3: an edge case (a stray self-link, or a link into a locked folder, e.g. on a shared volume), but the only remedy is deleting the link, since excluding it does not help.
- Suggested issue: "[P3] A link loop or unreachable link target in a source folder fails the build regardless of its type and of exclude". Fix: apply `exclude` and the file-type check by the link's own name before reading the target (a link's type is its name's extension, as `addFile` already assumes), and classify ELOOP explicitly; test the matrix {loop, EACCES on the way, dangling} × {source extension, other extension} × {excluded, not} for sources and modules, named and found.
